## 1. 背景・動機

### アイデア

タスク割当エージェント (現 PPO / 将来 ALMA Allocator) が、**タスクの配送状況に応じて稼働エージェント数を増減できる**仕様にする。割当方策の行動空間を `{タスク j, idle}` から `{タスク j, idle, off(退避) / on(投入)}` へ拡張し、fleet サイズ制御を「割当の一種」として同じ方策で扱う。

### なぜ LDRP で意味があるか (トレードオフ)

LDRP ではエージェントが増えるほど衝突・待機 (輻輳) が増え、**1 台あたりの移動効率は下がる**。一方でタスクを並列実行できる数は増える。つまり:

- エージェント数 ↑ → 移動効率 ↓ (輻輳デメリット) / タスク処理容量 ↑
- エージェント数 ↓ → 移動効率 ↑ / 処理容量 ↓

→ **タスク到着率・分布ごとに最適な稼働台数が存在する**はずで、これを配送状況から動的に学習・制御できれば、単なる省コストではなくスループット自体の改善が狙える (動的フリートサイジング × MARL)。

### 前提となる既知の事実 (2026-07 時点の調査結果)

| 部品 | 状態 |
|---|---|
| MAT-Dec actor の N 汎化 | per-agent 共有 MLP で重みは n_agents 非依存。**`obs_agent_id=False` で学習すれば異なるエージェント数にそのまま適用可** |
| MAT-Dec critic | 入力次元が `n_actions × n_agents` 連結で N 固定。ただし学習専用 (推論は actor 単独) |
| 推論経路 (test.py → PolicyRunner) | エージェントごとに `get_action(ag_idx, ...)` を呼ぶ構造なので、**呼ぶ回数を変えるだけで途中増減に自然対応**。ただし現 [PolicyRunner](../src/all_policy/policy_runner.py) は RNNAgent 専用 (`fc1.weight` を要求) で MAT-Dec モデルを読めない |
| drp_env | `agent_num` が `__init__` で固定。全配列 (goal_array / assigned_tasks / obs) が agent_num 長。スポーン/離脱 API なし |
| epymarl 学習基盤 | `EpisodeBatch` が `(batch, T, n_agents, …)` の固定形状。可変 N は非対応 |

## 2. 段階戦略

学習基盤まで触るとコストが大きいので 2 段階に分ける。**まず Phase A (方策実行時のみ変更可能な方式) から着手する。**

| Phase | 内容 | 増減の決定主体 | 学習基盤の変更 |
|---|---|---|---|
| **A. 実行時のみ** (先行) | 評価時にエージェント数を途中で増減できる。増減判断は固定ルール or 外部指示 | ルール (学習しない) | **不要** |
| **B. 増減も学習** (本命) | 割当エージェントが off/on を行動として学習 | 割当方策 | **必要** (下記 §5) |

Phase A は「env 側の増減基盤」の実装と検証を先に済ませる位置付けで、Phase B の土台になる。

## 3. 共通基盤: N_max + アクティブフラグ方式

可変長の配列伸縮 (動的スポーン) は env 全体・LaRe フック・SafeEnv まで波及して改修が大きい。代わりに:

1. **env は最初から `N_max` 体で生成**する (配列形状は全て N_max 固定)
2. 各エージェントに `active[i]` (bool) フラグを持たせる
3. 増減 = フラグの ON/OFF 切替として表現する

非アクティブ機の扱い:

- **観測**: obs をゼロ埋め (または退避状態を示す固定値)
- **行動**: `avail_actions` を「待機のみ」に制限 (epymarl の avail_actions 機構がそのまま使える。MAT-Dec は `logit[avail==0] = -1e10` でマスク済み)
- **衝突判定**: 除外 (退避ノードに居る想定。物理的にマップ上のノードを占有すると邪魔になるため、専用退避ノード or マップ外扱いにする)
- **報酬**: 0 (または稼働コスト 0)
- **タスク割当**: 割当対象から除外

利点: EpisodeBatch も critic も固定形状のままで済み、**epymarl 側はほぼ無改修**。SMAC の「死亡ユニット」の扱いと同じパターン。

> **実装は [next_actions.md §10 Step 1](next_actions.md)** (2026-08-16 に 2 段階へ分割)。Step 1 = 本節のアクティブフラグ基盤 + 開始台数の抽選、Step 2 = §3 末尾の off/on 遷移。
>
> **この基盤には増減制御とは独立の用途がある**: 開始時の実効台数を毎エピソード引き直せば、経路方策に「N_max のうち何体が動いているか」の分布を経験させる**台数汎化学習**になる ([next_actions.md §9 方式3](next_actions.md))。エピソード途中の増減 (Step 2) を待たずに学習を回せるため、実装順序上は Step 1 が先。
>
> ただしこれは **実効台数の汎化であって系列長の汎化ではない**。トークン数は常に N_max なので、N_max を超える台数へのゼロショットは未経験領域になる (next_actions.md §9 冒頭の (A)/(B) 切り分けを参照)。
>
> **実装時に判明した追加事項** (2026-08-16): 非アクティブ機の obs は**ゼロ埋めしない** (station に静止した agent として見せる。上の「観測」の記述は Phase A 検討時のもので、[next_actions.md §10-0 判断 2](next_actions.md) で station 静止に確定した)。また **SafeEnv (`wrapper/safe_marl.py`) の act8 も除外が要る**: 非アクティブ機が毎ステップ station を行き先として出し続けるため、除外しないと station へ向かうアクティブ機が強制停止させられる。

### 設計判断が必要な 3 点

1. **退避中の機体の居場所**: 専用退避ノード (デポ) を map に追加するか、マップ外扱い (座標を無効値) にするか。
   - **検討中の第一候補: 既存の station ノードを退避/投入拠点として使う**。LDRP のマップ定義 ([node.csv](../src/main/drp_env/map/) の `station` 列) には既に station フラグ付きノードがあり (例: map_aoba00 は 1 個)、これを **off したエージェントの待機場所 / on するときの湧き出し口**に使う。
   - 利点: **マップにデポを新設しなくてよい** (従来マップと非互換にならない = [CLAUDE.md](../CLAUDE.md) の baseline 不変条件に整合しやすい)。station は現実の充電/待機ステーションの意味付けとも合う。
   - 検討事項: (a) station ノードが 1 個だと投入/退避が 1 拠点に集中し、そこが輻輳源になりうる → 複数 station を持つマップの用意 or station 上は衝突判定を緩める。(b) off 中の機体が station ノードを物理占有すると経路の邪魔になる → station 上は「非アクティブとして衝突除外」扱いにする (§3 の非アクティブ機の衝突判定と同じ)。(c) 参入時のスポーン地点 = 最寄り station にするか固定 station にするか。
2. **離脱時のタスク解放**: 離脱する機体が配達中タスクを持つ場合の扱い。ピック前なら `current_tasklist` に戻す ([alma_integration.md §3.4](alma_integration.md) の再割当と同じ解放処理 `assigned_list[old_idx] = -1` が流用可能)。**ピック後 (積荷あり) は離脱禁止にするのが簡明** (配達完了まで off を無効化)
3. **参入/離脱の遷移セマンティクス**: 即時テレポートか、「デポへ帰投 → 到着後に非アクティブ化」か。簡易版 (即時退避) から始める

### 確定した増減メカニズム (2026-08-10 決定)

上記 3 点のうち 1 (居場所 = station) と 3 (遷移 = 帰投方式) を以下のとおり確定する。増減の決定主体はタスク割当エージェント (§1 のとおり)。

- **減らす (off)**: 割当方策が**タスク割当と同じ形式で station ノードをゴールとして割り当てる** (station = 擬似タスク)。機体は経路方策で station へ帰投し、「**ゴール = station ノード かつ station ノードに到着**」した時点で非アクティブ化 (いなくなる)。即時テレポートは採らない。
  - 帰投走行が切替コストとして報酬 (move/wait) に自然に乗るため、§5.4 対策 1 (切替コストの報酬反映) を**構造的に内包**する。
  - 帰投中はアクティブ扱い (衝突判定・台数カウントあり)。
- **増やす (on)**: **非アクティブ機への既存タスクの割当そのもの**を参入行動とする。**1 ステップに最大 1 体**まで。参入機は **station ノードから出発**する。
  - 専用の `on` 行動は不要 (割当対象に station 上の非アクティブ機を含めるだけ)。
  - タスクが無ければ参入できない = **需要駆動の参入** (§3 ウォームアップ論点の「需要は外生」と整合)。
  - 「最大 1 体/step」は §5.4 対策 3 (粒度制限) を兼ねる。

**帰結**:

- §5.1 の行動空間拡張は抽象案 (`off` / `on` 専用行動) より小さくなる: 「割当先候補に station を追加」+「割当対象に非アクティブ機を含める」の 2 点で済む。
- off にできるのは**空荷の機体のみ**: タスク保持中の機体には (通常タスクと同じ割当マスクで) station を割り当てられない → §3-2 の「ピック後は離脱禁止」がマスク流用でそのまま実現される。
- 経路方策 (MAT/QMIX) から見ると station ゴールは通常ゴールと区別不要 (obs の goal one-hot に station ノードが入るだけ) → **経路方策は無改修**。非アクティブ化後の扱いだけ §3 のアクティブフラグ方式に従う。

### エピソード初期化・ウォームアップ (t=0 の扱い)

**論点**: 疎な到着 (Bernoulli `p` 小, [future_work §4](future_work.md)) では t=0 でタスクがほぼ無く、N_max 体が一斉に暇 → フリート方策が**開始直後に大量 off** しがち。これを「ウォームスタート (頭に手持ちタスクを用意)」で避けたくなるが、**やり方を誤ると需要モデルを壊す**。

**却下する案: 初期タスク数 = agent_num**

- **需要が台数の関数になる (最重要 NG)**: 動的フリートサイジングの前提は「需要は外生 = 台数と無関係、それに台数を合わせる」。初期タスクを agent_num にすると「台数が多い=需要も多い」と因果が逆転し、**問題設定の根幹が崩れる**。
- **真の需要を隠す**: 疎なら N_max は過剰で削減が正解。初期に agent_num 個積むと削減を不当に抑制するバイアス。ユーザーが懸念した「開始時の大量削減」は**低需要では正しい挙動**なので構造で潰さない。
- **人工的な初期バースト**が疎/密シナリオと交絡。
- **N 間比較が壊れる**: N ごとに初期需要が変わり「同じ需要・違う台数」の比較不能。

**採る対処 (需要を歪めずに t=0 過渡を緩和)**:

| 対処 | 効果 |
|---|---|
| **ヒステリシス / 切替コスト** ([§5.4](#54-振動-thrashing-対策)) | off→on 往復 (thrashing) を防ぐ。「頭で減らしてすぐ戻す」churn の本丸対策 |
| **start-low-and-grow** | 初期アクティブ数を N_max でなく少なめにし、需要に応じて増やす。「大量に出して削る」を根本回避 |
| **ウォームアップ (burn-in)** | 最初の K ステップを報酬/評価から除外。フリートが落ち着くまでの過渡を無視 |
| **初期アクティブ数のランダム化** ([§5.3](#53-学習基盤の変更点-ここが大きい)) | 学習時に 2〜N_max でランダム化。特定初期値への過適合防止。**→ [next_actions.md §10 Step 1](next_actions.md) で実装 (`randomize_initial_active` / `min_active_agents` / `max_active_agents`)。非アクティブにする index も毎回引き直す** (後ろ固定だと MAT の自己回帰順序が「位置 k 以降は動かない」を覚えるため) |
| (どうしても初期プールを積むなら) **agent_num と独立**な固定数 / 定常キュー長相当 | 需要を外生に保ったまま過渡だけ緩和 |

**方針**: ウォームスタートは「agent_num 連動」でなく **ウォームアップ + start-low-grow + ヒステリシス**で対処する。削減自体は低需要下では正しいので抑制しない。RHCR/LoRR の「各エージェントに開始時タスク1個」慣習は固定フリート前提の話であり、台数可変の本設計にそのまま持ち込まない。

### マスク方式の実装状況と性能上の代償 (2026-09-05 調査)

台数可変は **N_max 固定 + 行動マスク**で実装されている。ネットワークの入力エージェント数は
`agent_num` のまま変えず、非アクティブ機の行動を潰す。

#### どこでマスクしているか

| 側面 | 非アクティブ機の扱い | 実装 |
|---|---|---|
| 経路の行動空間 | 現在ノードに留まる 1 手だけ avail | `_get_avail_agent_actions` (~697 行) |
| タスク割当の行動空間 | スロットを丸ごとマスク。`off` も `can_off` でなければマスク | [ppo.py](../src/task_assign/task_policy/ppo.py) の `mask` |
| 衝突判定 | 除外 (マップ上にいない扱い) | `collision_detect(..., active=...)` |
| 報酬 | 0 (`start_ori_array[i] = goal_array[i]`) | `reward()` |
| 観測 (FOV) | **除外されていない** | [fov_wrapper.py](../src/main/drp_env/state_repre/wrapper/fov_wrapper.py) |

```python
# _get_avail_agent_actions — 非アクティブ機は「その場に留まる」1 手だけ
if self.use_dynamic_agents and not self.active[agent_id]:
    node = int(self.current_start[agent_id])
    avail_actions_one_hot = np.zeros(n_actions)
    avail_actions_one_hot[node] = 1
    return avail_actions_one_hot, [node]
```

観測が除外されていない件は [future_work.md §9](future_work.md#9-非アクティブ機の観測と衝突判定の不整合) に切り出した。

#### QMIX の state にアクティブフラグが入っていない

タスク割当側と経路側で扱いが割れている。

| 方策 | state にアクティブ情報が入るか | 根拠 |
|---|---|---|
| PPO タスク割当器 | **入る** (active を連結している) | [ppo.py](../src/task_assign/task_policy/ppo.py) の `create_state` 末尾 |
| QMIX / VDN の mixer | **入らない** | [epymarl/src/envs/\_\_init\_\_.py](../src/epymarl/src/envs/__init__.py#L145) の `get_state()` が `np.concatenate(self._obs)` のみ |

```python
def get_state(self):
    return np.concatenate(self._obs, axis=0).astype(np.float32)   # obs の連結だけ
```

off 機の obs は「ステーションノードにいる」という one-hot なので、
**ステーションに停車している稼働機と区別がつかない**。
QMIX の単調性制約の下では、同じ state でも稼働台数が違えば最適な `Q_tot` は変わるはずだが、
mixer はその台数を state から読み取れない。

#### マスク方式の代償 (性能低下が起こりうる経路)

| # | 何が起きるか | なぜ |
|---|---|---|
| 1 | **無意味なサンプルが buffer を埋める** | off 機のステップも遷移として記録される。行動は 1 通り、報酬は 0 なので学習信号を持たない。`max_active_agents=7` で 2 台稼働なら **5/7 のサンプルが無駄** |
| 2 | **mixer が稼働台数を見られない** | 上記のとおり state に active が無い。台数によって `Q_tot` のスケールが変わるのに区別できず、混合が台数間で平均化される |
| 3 | **クレジット割当が薄まる** | off 機の Q も `Q_tot` に足される。稼働機の寄与が相対的に小さくなる |
| 4 | **off 機がソフト障害物として残る** | 観測では占有として見えるので、他機が不要に迂回する ([future_work.md §9](future_work.md#9-非アクティブ機の観測と衝突判定の不整合)) |

1〜3 はいずれも **稼働台数を絞るほど悪化する**。「台数を減らすと効率が上がる」ことを示したいのに、
台数を減らすほど学習が不利になる、という向きの逆行が起きうる。

#### 代替案

| 案 | 内容 | コスト | 代償の解消 |
|---|---|---|---|
| **A. 現行 (マスクのみ)** | N_max 固定、非アクティブは 1 手に固定 | 済 | — |
| **B. 観測からも消す** | `fov_wrapper` に `active` を渡し、非アクティブ機を占有から外す | 小 (1 ファイル) | 4 |
| **C. state に active を足す** | `get_state()` を obs 連結 + active フラグに変える。`get_state_size()` も併せて +N | 中 (epymarl の env ラッパ。**state 次元が変わるので既存モデルと非互換**) | 2, 3 (部分的) |
| **D. 学習時に非アクティブ機を間引く** | learner の loss で off 機の TD 誤差をマスクする | 中 (epymarl の learner) | 1, 3 |
| **E. 可変長アーキテクチャ** | TransfQMix / MAT でエンティティ集合として扱い、非アクティブ機を入力から外す | 大 (obs 表現の改修。§10 参照) | 1〜4 すべて |

**B → C → D の順で効果対コストが良い**。E は根本解だが §10 のとおり obs を
エンティティ集合に分解する改修が必要で、別タスク扱いにする。

C は state 次元が変わるため、**既存の学習済みモデルが読めなくなる**点に注意
(`src/all_policy/models/safe/` の 20 件超が対象)。導入するなら台数可変の条件だけに限定するか、
モデル命名で世代を分ける必要がある。

#### そもそも代償が出ているかの測り方

理屈だけでは効いているか分からないので、**同じ台数で fixed と dynamic を比べる**のが直接的。

```text
条件 X: use_dynamic_agents=False, agent_num=5           (従来の固定 5 台)
条件 Y: use_dynamic_agents=True,  min_active=max_active=5 (台数は動かないがマスク経路を通る)
```

Y は台数が動かないので、**X との差はマスク方式そのもののコスト**になる。
差が無ければ 1〜3 は無視してよく、B (観測) だけ直せば済む。
差が出るなら C / D に進む価値がある。この比較は seed 5 本ずつで
[run_collector.md](run_collector.md) の集計にそのまま乗る。

## 4. Phase A: 方策実行時のみ変更可能な方式 (先行実装)

学習は一切変えず、**評価 (test.py / runner.py) でのみ**エージェント数を途中増減できるようにする。

### 4.1 必要な実装

| # | 対象 | 内容 | 規模 |
|---|---|---|---|
| 1 | [src/main/drp_env/drp_env.py](../src/main/drp_env/drp_env.py) | `active` フラグ + §3 の除外処理 (衝突・割当・報酬)。`set_agent_active(i, bool)` のような外部 API | 中 |
| 2 | [src/all_policy/policy_runner.py](../src/all_policy/policy_runner.py) | MAT-Dec ローダ追加: state_dict から `decoder.*` キーのみ抽出して `Decoder(input_shape, n_actions, n_embd)` に load する分岐 (critic の `encoder.*` は捨てる)。`obs_agent_id=False` 学習モデルが前提 | 小 (〜40 行) |
| 3 | [runner.py](../runner.py) | 評価ループで非アクティブ機をスキップ (`if not active[i]: continue`)。増減トリガの注入 (ステップ数指定 or 未割当タスク数の閾値ルール) | 小 |

### 4.2 増減トリガ (Phase A では学習しない)

固定ルールで動作検証する。例:

- 未割当タスク数 > 閾値 T_on で 1 台投入 / タスク枯渇が N step 続いたら 1 台退避
- または実験シナリオとして「step 200 で 2 台追加」のような外部スケジュール指定

これで「増減が正しく動く env」を学習なしで検証でき、かつ **固定 N との性能比較 (増減にそもそも価値があるか) を先に確認できる**。

### 4.3 前提条件

- 経路方策は `obs_agent_id=False` で学習した MAT-Dec (actor が N 非依存になる唯一の構成)
- 同一マップ (n_nodes が変わると obs 次元が変わり転移不可)
- 密度ロバスト性の注意: N 固定で学習した actor は特定の混雑度に過適合しうる。Phase A の評価で「5 体学習 → 7 体実行」の性能劣化度を測ること自体に意味がある

## 5. Phase B: 増減を割当エージェントが学習する方式 (本命)

### 5.1 行動空間の拡張

> **2026-08-10 更新**: §3「確定した増減メカニズム」により、off = station を擬似タスクとして割当 / on = 非アクティブ機への通常タスク割当 (1 step 最大 1 体) に確定。以下の抽象案のうち専用 `on` / `stay-off` 行動は**不要**になり、拡張は「割当先に station を追加」+「割当対象に非アクティブ機を含める」に縮小される。

割当方策 (PPO / ALMA Allocator) の per-agent 行動 (抽象案。実装は上記確定版に従う):

```
b^a ∈ {タスク 0..|I|-1, idle, off}      # アクティブ機
b^a ∈ {on, stay-off}                     # 非アクティブ機
```

ALMA の pointer-net 構造なら「off」「on」を idle と同様の**学習可能な専用埋め込み**として追加するだけで済む ([alma_integration.md §6.1](alma_integration.md) の idle_embedding と同型)。

### 5.2 報酬設計 (最重要ハイパラ)

稼働コストを入れないと「常に全員 ON」に縮退し、強すぎると全員 OFF になる:

```
R = (タスク完了報酬) − c_active × (アクティブ台数) × Δt
```

- `c_active` (per-step 稼働コスト) が本質的なチューニング対象
- **対照実験**: コスト項なし (輻輳ペナルティ = collision/wait だけで最適台数に自然に落ちるか) vs コスト項あり。前者で成立するなら報酬設計がシンプルになる

### 5.3 学習基盤の変更点 (ここが大きい)

Phase B が「学習時にも大きな変更が必要」となる理由と、N_max 方式による回避策:

| 問題 | N_max + アクティブフラグでの解決 |
|---|---|
| EpisodeBatch の固定形状 | `n_agents = N_max` で確保すれば形状は不変。**epymarl のテンソル配管は無改修** |
| MAT-Dec critic の入力次元 | N_max 固定なので形状問題なし。ただし非アクティブ機の情報が critic 入力に混ざるため、ゼロ埋め or アクティブマスクを attention に渡す改修が望ましい |
| 非アクティブ機の学習信号 | 「待機のみ」の avail_actions マスクで行動は縛れるが、**loss 側でも非アクティブ機のエントロピー/方策勾配をマスクする**必要あり (mat_learner の mask 拡張) |
| 割当方策の遅延信用割当 | 台数変更の効果は数十〜数百 step 後に出る。**LaRe-Task の proxy 報酬と相性が良い** (割当決定の品質を直接反映)。ALMA の N_t 区間累積報酬でも可 |
| actor の密度過適合 | **学習中に初期アクティブ台数をランダム化 (2〜N_max)** して密度に汎化させる。既存のカリキュラム学習 (CL) の続きとして位置付く |

### 5.4 振動 (thrashing) 対策

ON/OFF が毎ステップ揺れる問題。[alma_integration.md §3.4](alma_integration.md) の再割当振動と同じ構造なので同じ緩和策を流用:

1. 切替コストを報酬に反映 (帰投・投入の無駄走行が学習信号に入るようにする)
2. ヒステリシス / 最小滞留時間 (off にしたら最低 K step は on にできない)
3. イベント駆動の粒度制限 (毎 step でなくイベント時のみ増減判断)

## 6. 評価設計

### 指標

- タスク完了数 (従来指標)
- **agent-step あたり完了数** (= 効率。増減制御の主張はこれで立てる)
  - 定義: $\text{efficiency} = \frac{\text{completed tasks}}{\sum_t \text{active agents at step } t}$
  - これを主効率指標とし、固定 N と動的増減の比較で直感的に扱う
- **平均稼働台数** (= コスト指標)
- **平均アクティブ率** (= 平均稼働台数 / N_max)
- **タスク待機時間** (作成 → ピックまで)
- **1 タスクあたりの平均移動距離** / **平均走行距離** (経路効率の補助指標)
- **増減回数 / 振動率** (thrashing の抑制度)
- **cost-adjusted score** (任意): $\text{completed tasks} - c_{active} \times \text{active-agent steps}$。報酬設計の感度実験で使う

### 方策評価フェーズでの実装方針

これらは学習ループではなく、**評価 (test.py / runner.py) の rollout 終了時に集計する**のが自然。

- エピソードごとに、完了タスク数・累積アクティブエージェントステップ・平均待機時間・走行距離・増減回数を記録する
- 複数エピソード後に平均/標準偏差を計算し、標準的な policy evaluation ログとして出力する
- 主要出力は「効率 (completed / active-agent-step)」と「コスト (平均アクティブ台数)」の 2 軸とし、パレート図に載せる

これで、学習中の loss とは独立に、方策の実運用効率を評価しやすくなる。
### ベースライン比較

| 条件 | 内容 |
|---|---|
| 固定 N_max | 全台数常時稼働 (現状) |
| 固定 N (少数) | N = 2, 3, ... の各固定値 |
| ルール増減 (Phase A) | 閾値ルール |
| **学習増減 (Phase B)** | 割当方策が off/on を学習 |

**主張の形**: 学習増減が「固定のどの N よりもパレート上で良い」(完了数 − 稼働コストの両立) ことを示せれば強い。タスク到着率を変えたシナリオ (疎/密/バースト) で優位性が出るかも見る。

## 9. 関連環境・先行事例 (参考)

### 9.1 エピソード途中でエージェント数が変わる環境 (構造が近い)

**いずれも増減はルールベース (外部スケジュール / 環境内部ルール) で決まり、方策が台数を決める環境は無い。**
この「決定主体」の空白が本設計の position ([aamas_submission.md §3](aamas_submission.md))。

**書誌情報 (投稿時に引く査読版) は [aamas_submission.md §10.1](aamas_submission.md) に集約。**
本節は「仕組みと LDRP への流用可否」を扱い、引用キーは重複させない。

#### 仕組みと LDRP への流用

| 環境 | 増減の仕組み | 決定主体 | LDRP が借りられるもの |
|---|---|---|---|
| **Flatland** | 列車が出発時刻に**参入**し目的地到着で**退出**。グリッド上の衝突・デッドロックあり | 外部スケジュール | **構造的に最も近い** (グラフ上 + 輻輳 + 参入/退出スケジュール)。参入トリガ設計 (出発時刻) は Phase A のルールトリガそのもの |
| **SMAC / SMACv2** | ユニットが戦闘で**死亡** = 途中減少 (単調減少のみ、復活なし)。死亡ユニットは obs ゼロ埋め + `avail_actions` を no-op のみに制限 | 環境内部ルール (戦闘) | **§3 の N_max + アクティブマスクの実装パターンそのもの**。epymarl は SMAC 用に作られており、**avail_actions 経由の無効化の配管は現学習基盤に既に通っている** → 実装の写経元 |
| **Melting Pot 2.0** | zap ビームで player を**一時 removal** (Clean Up: 50 step, Allelopathic Harvest: 25 step) → 復帰。**API 上の player 数は不変**で「各エピソードは常に同じ player 数・同じ role」 | 環境内部ルール (他 player の zap) | **スロット固定 + 一時無効化という点で §3 と同型**。「N_max 枠を保持したまま稼働状態だけ切替える」設計の先行例 |
| **Neural MMO** | spawn と死亡でオープンエンドに population が変動 | 環境内部ルール (spawn/HP) | 参入 (spawn) 側のセマンティクス |
| **MAgent2** | HP 0 で死亡し盤面から除去 = **単調減少**。同梱環境 (battle 等) は `add_agents()` を reset のマップ生成時にしか呼ばず**エピソード中の respawn は無い** (GridWorld エンジン自体は spawn API を持つ) | 環境内部ルール (HP) | 可変 N での観測設計 (局所観測 + 固定次元) |
| **Multi-Agent Craftax** ([arXiv:2511.04904](https://arxiv.org/pdf/2511.04904)) | オープンエンド・大規模の動的 population | 環境内部ルール | 最近のベンチマーク動向 |

#### 台数が固定の環境 (対比用)

Google Research Football / VMAS / RWARE はいずれも構築時の config で `n_agents` が固定され、エピソード内でもエピソード間でも変化しない。**LDRP と同じ倉庫搬送ドメインの RWARE ですら固定**である点が対比として効く。

### 9.2 参入/退出への適応を研究対象にした系譜 (Open MAS / Ad Hoc Teamwork)

- **GPL: Open Ad Hoc Teamwork Using Graph-based Policy Learning** (ICML 2021): チームメイトが途中で入れ替わる設定を graph NN で扱う。**可変数エージェントのネットワーク表現** (集合入力・GNN) の代表例。LBF / Wolfpack を open 化した改造例としても参考になる。MAT-Dec actor は per-agent MLP なので当面不要だが、critic を賢くする場合の参考
- **Transferable MARL with Dynamic Participating Agents** ([arXiv:2208.02424](https://arxiv.org/pdf/2208.02424)): 学習途中でエージェント数を変える転移の研究。§5.3 の「初期台数ランダム化」の裏付けに近い
- **オープンエンド協調の定式化 (DOSBG 系)** ([AAMAS 2025](https://link.springer.com/article/10.1007/s10458-025-09723-7)): 参加/離脱 + タスクストリームの定式化。論文化する際の問題設定の参考

### 9.3 フリートサイジングをドメインとして扱う系譜 (報酬設計の参考)

- **ライドヘイリング fleet management** (Lin et al., KDD 2018, [arXiv:1802.06444](https://arxiv.org/abs/1802.06444)): 車両の再配置・稼働を MARL で制御。**「稼働台数 × コスト vs サービス充足」の報酬設計** (§5.2 の `c_active`) の先行例
- **MAPD サーベイ** ([arXiv:2203.07092](https://arxiv.org/abs/2203.07092)): LDRP と同一のタスク定式化。MAPD 文献では必要台数は**オフライン事前決定が通例**で、「割当方策がオンラインで台数を決める」のはギャップ = **本設計の新規性の主張点**に使える
- **Scalable MARL for Warehouse Logistics** ([arXiv:2212.11498](https://arxiv.org/pdf/2212.11498)): 倉庫でロボット + 人間ピッカーの大規模割当。中央割当 + 移動エージェントの階層構造が ALMA 設計と近い

### 使い分けの目安

- **実装の写経元**: SMAC の死亡マスキング (epymarl 内の既存配管) → §3
- **参入/退出セマンティクス**: Flatland (スケジュール参入・到着退出) → §4.2
- **可変 N のネットワーク表現**: GPL → Phase B の critic 改修時
- **報酬・評価設計**: ライドヘイリング系 (稼働コスト) + MAPD サーベイ (新規性の位置づけ) → §5.2 / §6
